Why this matters

Coupling: how tightly parts are tied together

Whenever one part of the code relies on another, a change in one can ripple into the other. Some of this is normal and necessary.

Parts that many others rely on are risky to change, because a mistake spreads to everything that uses them. Parts that rely on many others break easily, because any of those can change under them. Fewer connections, all pointing the same way, make code cheaper to change, test and hand over.

Cycles: parts that depend on each other in a loop

A cycle is a loop: A relies on B, and B, directly or through others, relies back on A. These parts all depend on each other, so none of them can be changed, tested or reused alone.

Work on any part of a loop tends to drag in all of it, and a bug in one part can surface in all of them. Breaking a loop is usually the first thing worth fixing, because it makes every part in it easier to work with.

How to read the numbers

Part
Each part is a group of files that share the first 3 levels of their namespace.
Relied on by (fan-in)
How many other parts of the code rely on this one.
Relies on (fan-out)
How many other parts of the code this one relies on.
Files relying on it (Ca)
How many files outside this group rely on it.
Files it relies on (Ce)
How many files outside this group it relies on.
Instability
How much this part is pushed around by changes elsewhere, from 0 (others lean on it) to 1 (it leans on others). Neither end is bad in itself: what matters is that parts others lean on stay stable, and that unstable parts are the ones you expect to change. "None" means the part has no connections to other parts.
Packages
How many third-party packages this part uses directly.
Untraced
References we could not trace; the real coupling may be higher.
Cycle
These parts all depend on each other, so none of them can be changed, tested or reused alone.
